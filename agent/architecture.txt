================================================================================
LINGUALOOP: ARCHITECTURAL DESIGN & SPECIFICATION
Conversational Voice Calling & Chatting System
================================================================================

1. EXECUTIVE SUMMARY & HIGH-LEVEL OVERVIEW
--------------------------------------------------------------------------------
LinguaLoop is an interactive language tutoring platform that features both:
  A) Text-based Chat: Standard request/response with Server-Sent Events (SSE) 
     token streaming over HTTP.
  B) Voice Calling: A full-duplex, low-latency, real-time voice conversational 
     loop powered by browser-native Web Speech APIs (STT & TTS), a bi-directional 
     WebSocket gateway, sentence-boundary chunking, and the Mastra Agent framework.

Key Architectural Highlights:
- Client-Side Edge STT: Transcriptions are processed directly on the user's browser 
  via native SpeechRecognition, avoiding massive audio bandwidth transmission and 
  eliminating costly server-side Whisper GPU inference.
- Full-Duplex WebSocket Gateway: Audio transcripts, bot speech events, and user 
  interruptions (barge-in) flow over a persistent connection (ws://localhost:5000/audio-stream).
- Sentence Boundary Chunking: LLM tokens are gathered until sentence boundary punctuation 
  ([.!?]) is reached, sending discrete natural sentences to the client for immediate 
  Text-To-Speech (TTS) synthesis without waiting for the full response.
- Barge-in & Interruption Management: If the user begins speaking while the AI is talking, 
  client-side speech synthesis is cancelled immediately, and an INTERRUPT event aborts 
  the server-side LLM generator via an AbortController.
- Distributed Session & Memory Tracking: Redis manages real-time call states 
  (connected, streaming, interrupted, closed) with TTLs, while MongoDB & Mastra 
  persist conversation threads, role-playing personas, and message history.

2. CORE LIBRARIES & TECHNOLOGY STACK
================================================================================

A) CLIENT-SIDE LIBRARIES & BROWSER APIS:
- Web Speech Recognition API (window.SpeechRecognition / window.webkitSpeechRecognition):
  Client-side native Speech-To-Text (STT). Produces interim and final transcripts.
- Web Speech Synthesis API (window.speechSynthesis / SpeechSynthesisUtterance):
  Client-side native Text-To-Speech (TTS). Speaks received text with configurable 
  languages and voices.
- Native WebSocket API (window.WebSocket):
  Persistent bi-directional connection to the backend voice gateway.
- React 19 & TypeScript:
  UI state management, voice hooks (useVoiceChat.ts), and tutor components (VoiceTutor.tsx).
- Fetch & ReadableStreamDefaultReader:
  Used by chatService.ts for reading SSE text chat streams over HTTP.

B) SERVER-SIDE LIBRARIES & FRAMEWORKS:
- ws (^8.21.3):
  Lightweight, high-performance WebSocket server in Node.js attached to the HTTP server.
- @mastra/core (1.64.0):
  Agent orchestration framework managing system prompts, language tutor personas, 
  streaming LLM interaction, and tool integration.
- @mastra/memory & @mastra/mongodb:
  Persistent agent memory across conversational turns, indexed by conversationId and userId.
- ioredis (^6.0.0):
  Fast in-memory Redis client tracking active voice sessions, call statuses, and activity heartbeats.
- express (^5.2.1) & http:
  HTTP server hosting the REST API, auth middleware, and the underlying server for the WebSocket gateway.
- mongoose (^9.9.5):
  Object Data Modeling (ODM) for MongoDB user and conversation persistence.

4. AUDIO TRANSCRIPTION & DATA TRANSPORT (STEP-BY-STEP)
================================================================================

Step 1: Audio Capture & Speech-to-Text (STT) with 3-Second Pause Detection
- When the user starts a call (startCall()), the hook requests microphone access 
  via navigator.mediaDevices.getUserMedia({ audio: true }).
- It instantiates window.SpeechRecognition.
- Configuration settings:
    recognition.continuous = true;    // Continuous listening across natural sentence pauses
    recognition.interimResults = true;// Real-time partial results for responsive UI
    recognition.lang = 'en-US';
- As the user speaks, recognition.onresult fires:
    - Interim and finalized phrases accumulate into a live transcript buffer.
    - Whenever user speech/voice is detected, any existing silence timer is reset.
    - 3-Second Silence Debounce: A 3000ms timer runs. Only when the user has paused 
      speaking with zero voice detected for at least 3 full seconds is the accumulated 
      sentence finalized and sent.

Step 2: WebSocket Payload Transmission & Instant Auto-Mute
- The finalized text is packaged into a JSON payload and sent over the WebSocket:
    {
      "type": "USER_SPEECH",
      "sentence": "Hello, how are you today?",
      "text": "Hello, how are you today?"
    }
- Immediate Auto-Mute: As soon as USER_SPEECH is dispatched after the 3-second pause, 
  the client immediately sets isProcessing = true, aborts SpeechRecognition, and mutes 
  the microphone. This guarantees that ambient noise or accidental user utterances 
  during LLM thinking do not trigger spurious requests or abort in-flight responses.
- Query parameters passed during the initial WebSocket handshake identify the caller:
    ws://localhost:5000/audio-stream?conversationId=<UUID>&userId=<ID>&voiceId=<VOICE>

Step 3: Server Ingestion & LLM Processing
- voice.controller.ts receives the payload, emits AI_PROCESSING_START, and passes 
  it to voiceService.processSentence().
- voiceService manages an AbortController instance for this conversationId.
- It invokes the Mastra agent stream:
    const mastraStream = await agent.stream(
      [{ role: 'user', content: sentence }],
      { memory: { thread: conversationId, resource: userId } }
    );
- MongoDB retrieves past thread context and injects it into the prompt.

Step 4: Sentence Boundary Buffering (Latency Optimization)
- Instead of waiting for the full LLM response or streaming fragmented single tokens, 
  voiceService loops through mastraStream.textStream:
    let buffer = '';
    for await (const token of mastraStream.textStream) {
      buffer += token;
      // Match sentence endings (. ! ?)
      if (buffer.match(/[.!?]\s*$/)) {
        const completeSentence = buffer.trim();
        onAiSentence(completeSentence);
        buffer = '';
      }
    }
- As soon as each complete sentence is formed, the server sends:
    {
      "type": "AI_SPEECH",
      "text": "I am doing well! What would you like to practice today?"
    }
- Once all tokens are processed, the server signals turn completion:
    {
      "type": "AI_TURN_COMPLETE"
    }

Step 5: Client-Side Audio Playback (TTS) & Auto-Unmute
- useVoiceChat.ts intercepts incoming AI_SPEECH events into an utterance queue.
- Sentences are synthesized and played sequentially through window.speechSynthesis.
- While audio is playing:
    - isAiSpeaking is set to true.
    - Microphone remains strictly muted to prevent acoustic feedback.
- Safe Auto-Unmute:
    - Once all queued utterances have completed playback AND the AI_TURN_COMPLETE 
      signal has been received, isAiSpeaking and isProcessing reset to false.
    - The client automatically unmutes the microphone and resumes speech recognition 
      after a 300ms settling delay.

5. BARGE-IN & INTERRUPTION MECHANICS (FULL-DUPLEX)
================================================================================

In human conversation, speakers often interrupt each other. LinguaLoop implements 
real-time barge-in:

1. User Speech Detection:
   If the user starts talking while isAiSpeaking is true, recognition.onspeechstart 
   or recognition.onresult fires immediately.
2. Instant Client Abort:
   - window.speechSynthesis.cancel() kills browser audio output instantly.
   - The client sends a high-priority interrupt message:
     { "type": "INTERRUPT" }
3. Server Abort:
   - voice.controller.ts receives INTERRUPT and triggers voiceService.handleInterrupt(conversationId).
   - The stored AbortController for that conversation triggers active.abort().
   - The Mastra LLM token generator terminates immediately, conserving tokens.
   - Redis updates the session status to "interrupted".

6. WHY THIS ARCHITECTURE WAS CHOSEN (DESIGN DECISIONS)
================================================================================

1. Client-Side Web Speech vs. Server-Side Whisper:
   - WHAT: Using the browser's native SpeechRecognition and SpeechSynthesis.
   - WHY: Server-side audio streaming requires encoding PCM/Opus, heavy network 
     bandwidth, WebRTC or chunked uploads, and costly GPU servers running Whisper. 
     Browser Web Speech API is free, natively hardware-accelerated, provides 
     instantaneous transcriptions, and has zero server GPU overhead.
   - HOW: Controlled via React hook useVoiceChat.ts with automatic reconnection 
     and network error handling.

2. WebSocket vs. HTTP Polling / SSE:
   - WHAT: A persistent WebSocket gateway at /audio-stream.
   - WHY: Voice calls require full-duplex communication. The client needs to 
     receive AI speech while simultaneously being able to send interrupt signals 
     or user speech without initiating new HTTP handshakes.
   - HOW: Implemented via ws in voice.controller.ts.

3. Sentence-Boundary Chunking vs. Full-Text Waiting vs. Token Streaming:
   - WHAT: Buffering tokens on [.!?] before synthesizing.
   - WHY: Waiting for the full LLM paragraph creates 3 to 6 seconds of awkward 
     conversational silence. Conversely, feeding individual tokens to TTS sounds 
     broken, jerky, and unintelligible. Sentence chunking provides sub-second 
     time-to-first-audio while preserving natural prosody.

4. Redis Session Storage + MongoDB History:
   - WHAT: Dual database strategy.
   - WHY: Redis provides sub-millisecond ephemeral call status tracking (connected, 
     streaming, interrupted) and TTL heartbeats. MongoDB provides permanent, durable 
     storage for past conversation threads and grammar learning metrics.
